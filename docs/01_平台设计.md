## 2. 【关键】渲染规范

这一节是整份文档最重要的部分。渲染做错，实验结论就作废。

### 2.1 绝对禁止：高亮 hub

论文插图 `paper_figure.py` L134–137 把 hub 画成**红色、放大 1.6 倍**：

```python
if hubs:
    nx.draw_networkx_nodes(G, pos, ax=ax, nodelist=hubs,
                           node_size=int(sz * 1.6),
                           node_color='#e74c3c', alpha=0.9)
```

**用户实验绝不能这么做。** 原因：

| 任务 | 若高亮 hub 的后果 |
|---|---|
| **T4**「哪个节点连接更多？」 | 退化成「找红色的」——**任务完全失效** |
| **T1**「找出邻居」 | 被试会以红色节点为中心，产生系统性偏差 |

**规则**：所有节点**同一填充色、同一半径**。只有**目标节点**变成**蓝色填充**（`#2196f3`）——不放大、不改半径、不加描边（见 §2.3）。

### 2.2 归一化：**包围盒（fit-to-view）**【已定案】

```
对每个布局（每种算法产出的坐标）独立处理：
  1. 取该布局所有节点的坐标
  2. 算包围盒 w × h（原坐标单位）
  3. 留白 = 画布尺寸的 8%（每边）⇒ 可用区 = 画布的 84%
  4. scale = min( (canvas_w × 0.84) / w,  (canvas_h × 0.84) / h )
  5. 缩放后把包围盒中心平移到画布中心
```

> ⚠️ **注意量纲（文档早期版本的 bug）**：留白必须从**画布像素**里扣，不能从**原坐标**里扣。
> 早期写作 `pad = 0.08 × max(w, h)` 再用 `(canvas_w − 2·pad)/w`，**把原坐标单位当像素减了**——
> 实测会导致约 **75% 的图裁掉边界节点**，且 LPFD/KK/FR 全裁、FA2 不裁。
> **正确做法是先算 scale，再乘 0.84。**（代码已按修正版实现，本文档此前是旧的，现已同步。）

**为什么用这个 —— 三个参照物全都指向它：**

| 参照物 | 归一化方式 | 出处 |
|---|---|---|
| **GVRRI**（我们参照的已发表实验） | **包围盒 + 10% 留白** | `resistance.py::plot_network`：`ax.set_xlim(x_min - padding, x_max + padding)` |
| **我们的论文插图** | **包围盒 + 8% 留白** | `paper_figure.py` L139–146，每个子图 fit 自己的包围盒 |
| **用户的真实体验** | **fit-to-view** | 任何人打开一张图都是「适应窗口」 |

> 规格早期版本曾选用「中位边长归一化」（把典型边长映射到 40px），理由是「避免紧凑布局被放大」。
> **该选择已废弃** —— 它是三个参照物中的唯一异类，且会引入一个不必要的副作用：
> 跨度/中位边长 较大的布局会撑爆画布，触发 shrink-to-fit，反而把节点压到重叠。

**采用包围盒后**：

| | |
|---|---|
| **溢出** | **从定义上不可能发生** —— 缩放后必然铺满画布 |
| **不需要** | shrink-to-fit、尺寸下限、`k_min` 筛图、自适应节点半径 |
| **已知代价** | 紧凑的布局会被放大 → 节点看起来更分散 → 更容易读 |

**关于那个「代价」**：这不是渲染 artifact，而是**布局紧凑这一真实优势的正常体现**——在真实工具里适应窗口后确实如此。若某方法产出的布局天生紧凑，那用户在实用中确实会得到更分散的视图。

> ⚠️ **pilot 时必须验证**：**同时产出一套「中位边长归一化」的刺激**，对比两种渲染下结论方向是否稳定。
> 若方向一致 → 归一化选择不影响结论，通过。
> 若方向不一致 → 说明存在尺度效应，**必须在论文里讨论**。

### 2.3 视觉规格 —— 与 GVRRI 对齐

**为什么用这套**：GVRRI（Zhao et al., *C&G* 138:104641, 2026）的 pilot user study 用的是完全一致的视觉编码，且论文明确说明其目的是 *"to eliminate shape, size, or color variation biases"*。**沿用已发表实验的规格，审稿人无认知负担。**

| 项 | **规定值** | 来源 |
|---|---|---|
| **画布** | **900 × 620 像素**，白底 | GVRRI 原文 |
| **节点** | **灰色圆，半径 5 像素** | GVRRI 原文 |
| **边** | **灰色线，宽 2 像素** | GVRRI 原文 |
| **目标节点** | **蓝色填充** `#2196f3` | GVRRI 原文 |
| **被选中的节点** | **加红色描边** `#e53935`（宽 3px），**填充色不变** | GVRRI 的**扩展** —— 理由见下方 §2.3.1 |
| **节点 ID** | 图上**不显示**；选中的节点 ID 列在**左侧面板**，每项旁有垃圾桶图标可单独删除 | GVRRI 原文 |
| **平移缩放** | **必须提供** | GVRRI 原文 |
| **进度条** | 界面底部 | GVRRI 原文 |
| **节点大小 / 边宽** | **跨图、跨布局完全一致** | GVRRI 原文 |
| 边交叉 | 不特殊处理 | — |
| 图上文字标签 | **一律不显示**（避免语义干扰） | 我们的补充 |

### ⚠️ 三条我们必须偏离 GVRRI 的地方

| # | 偏离 | 理由 |
|---|---|---|
| **1** | **不能显示布局方法名或图名** | GVRRI 没有对照条件，不需要盲测；我们有**四种布局**，**必须盲测** |
| **2** | **目标节点不能暗示度数** | 他们的目标节点只是蓝色，不体现度数——我们**沿用**这一点，且要确保四种布局下高亮样式完全相同 |
| **3** | **不能高亮 hub** | GVRRI 不涉及；但论文插图 `paper_figure.py` L134–137 把 hub 画成**红色、放大 1.6 倍**，实验里**绝不能这么做**（见 §2.1） |

> **补充说明**：GVRRI **不提供旋转/缩放之外的额外控制**，也没有「重置视图」。我们沿用同样的最小控件集，避免界面复杂度成为混淆变量。

#### 2.3.1 「已选中」用描边而不是变色 —— 原因

GVRRI 原文是**目标节点蓝色、已选节点变红**（纯色替换）。我们**沿用蓝色目标**，但把「已选中」改为**红描边**：

```
普通节点   ●  灰填充，半径 5
目标节点   ●  蓝填充                ← 跟 GVRRI
已选中     ◉  保持原填充 + 红描边    ← 本次扩展
```

| 为什么 | 说明 |
|---|---|
| **不丢失目标标识** | 若「已选中 = 纯红」，则目标节点一旦被选中就失去蓝色标识——被试会分不清「哪个是我要找的」和「哪个是我选的」 |
| **T4 不受影响** | T4 是点击即提交，没有持续选中态，两个目标节点始终都是蓝填充 |
| **与 GVRRI 的偏离很小** | 只是给「已选中」加了一层描边；目标节点、普通节点的样式与 GVRRI 完全一致 |

> ⚠️ **论文里要写明这一点**：我们是 *"following GVRRI's visual encoding, with one extension: selected nodes receive a red outline rather than a red fill, so that the blue target marker remains visible when the target itself is selected."*

## 3. 【关键】配置系统 —— 所有功能必须可开关

> **开发要求**：实验设计仍在演进中（任务取舍、归一化方式、措辞变体都可能在 pilot 后调整）。
> **所有可变项必须做成配置项，不得硬编码。** 功能要**全部实现**，但通过配置控制是否启用——
> 例如 T2 默认关闭，但代码里必须完整可用，改一个布尔值就能开启。

### 3.1 配置文件

建议单文件 `src/js/config.js`，导出一个对象：

```javascript
export const CONFIG = {
  // ───────── 任务 ─────────
  tasks: {
    T1: { enabled: true,
          wording: 'factual' },      // 'factual' | 'perceptual'（GVRRI 的 VRR 措辞）
    T4: { enabled: true },
    T2: { enabled: false },          // ← 默认关闭，pilot 后决定
  },
  // practiceTrials = 各任务的题数上限，**仅对 enabled 的任务生效**
  //   T2 关闭时（默认）→ 练习 4 题（T1:2 + T4:2）
  //   T2 开启时        → 练习 5 题（T1:2 + T4:2 + T2:1）
  practiceTrials:  { T1: 2, T4: 2, T2: 1 },
  practiceFeedback: true,            // 练习是否给反馈

  // ───────── 实验因子 ─────────
  // LPFD = 本文方法；KK = 最强几何基线；FR / FA2 = 经典与现代力导向代表
  layouts: ['LPFD', 'KK', 'FR', 'FA2'],
  degreeLevels: ['low', 'high'],     // 低 = 度 2–8 ／ 高 = 度 ≥16（无上限）（见 02_数据方案.md §3.2）
  trialsPerCell: 2,                  // 每个 (layout × degree) 单元的图数 → 4×2×2 = 16 图
  assignment: 'latin_square',        // 'latin_square' | 'full_within'（见 §8）

  // ───────── 渲染（规格与 GVRRI 对齐，见 §2.3）─────────
  normalization: 'bounding_box',         // ✅ 已定案。备用值 'median_edge_length' 仅用于 pilot 对比
  targetMedianPx: 40,
  canvas: { width: 900, height: 620, background: '#ffffff' },
  nodeRadius: 5,                         // GVRRI：灰色圆，半径 5 像素
  edgeWidth: 2,                          // GVRRI：灰色线，宽 2 像素
  colors: {
    node:              '#9e9e9e',   // 灰 —— 普通节点填充
    edge:              '#9e9e9e',   // 灰 —— 边
    target:            '#2196f3',   // 蓝 —— 目标节点填充（GVRRI 做法）
    selectedOutline:   '#e53935',   // 红 —— 被选中节点的【描边】，不改变填充（见 §2.3.1）
    selectedOutlineWidth: 3,
  },
  highlightHubs:  false,     // ★ 必须为 false（见 §2.1）
  showNodeLabels: false,     // ★ 图上不显示节点标签
  showIdPanel:    true,      // 左侧面板列出已选节点 ID（GVRRI 做法）
  showProgressBar:true,      // 底部进度条（GVRRI 做法）
  enablePanZoom:  true,      // 平移缩放（GVRRI 做法）

  // ───────── 交互 ─────────
  interactions: {
    clickToToggle: true,             // T1：单击切换选中
    rubberBandSelect: true,          // T1：拖拽矩形框选
    freehandLasso: false,            // T1：自由手绘（默认关，需要时开）
    clickSubmitsT4: true,            // T4：点击即提交（不设确认按钮）
  },

  // ───────── 质量控制 ─────────
  attentionChecks: 2,
  breakEveryNTrials: 12,
  breakDurationSec: 30,
  fullscreenRequired: false,
  detectVisibilityChange: true,
  minRtMs: 1000,                     // 低于此值的 trial 标记为可疑

  // ───────── 问卷 ─────────
  survey: {
    demographics: true,              // 实验前
    literacy: false,                 // ✅ 已取消（无可用的验证量表，见 03 §6.3）。
                                     //    模块必须保留 —— 将来拿到 Zoss NVL 拿掉这行即可
    perTrialEase: true,              // 每 trial 一个 1–7 易读性评分（见 03 §6.4）
    perTrialEaseEveryN: 1,           // 设为 6 则每 6 题问一次
    nasaTlx: true,
    tlxWeighted: false,              // true = 15 对成对比较；false = 等权
    prevIs: false,                   // ⚠️ 适配性待确认（见 03 §6.5），默认关
    preference: false,               // 实验末的四布局并排排序（会破坏盲测，必须放最后）
  },

  // ───────── 落盘 ─────────
  storage: {
    mode: 'localStorage',            // 'localStorage' | 'post'
    endpoint: null,                  // mode === 'post' 时使用
    autosaveEveryTrial: true,
  },
};
```

### 3.2 必须可配置的清单（逐项核对）

| # | 配置项 | 为什么需要可配 |
|---|---|---|
| 1 | **启用哪些任务**（T1 / T4 / T2） | T2 要能随时开关 |
| 2 | **T1 的措辞变体**（事实型 / 感知型） | pilot 后可能切换为 GVRRI 的 VRR 措辞 |
| 3 | **归一化方式** | ✅ 已定案「包围盒」；`normalization` 配置项保留两个取值，供 pilot 对比 |
| 4 | **是否高亮 hub** | 必须永远为 `false`，但要能配置（便于验证） |
| 5 | **交互方式组合** | 手绘 lasso 要能开关 |
| 6 | **布局集合** | 可能增删基线 |
| 7 | **度数档位与每单元图数** | 决定试次规模 |
| 8 | **试次分配方式** | Latin square vs 全被试内（见 §8） |
| 9 | **练习题数与反馈开关** | pilot 调整 |
| 10 | **落盘模式与端点** | localStorage（实验室）vs POST（Prolific） |
| 11 | **问卷各部分开关** | 可能要精简 |
| 12 | **质量控制参数** | attention check 数量、休息间隔、RT 下限 |

### 3.3 实现要求

- 配置文件是**唯一**的硬编码点，其它模块一律从 `CONFIG` 读取
- 启动时打印一份**生效配置摘要**到控制台，并写入被试数据文件的 `config` 字段（便于事后核对用的是哪套配置）
- 所有配置项要有**默认值**，缺省时能跑起来
- 未知的配置键**报错而不是静默忽略**（避免拼写错误导致配置不生效）

## 5. 流程状态机

```
WELCOME
   ↓
CONSENT          知情同意（勾选后才能继续）
                 ★ 文本见 `06_知情同意书.md`；必须记录时间戳
   ↓
DEMOGRAPHICS     年龄 / 性别 / 专业 / 图论熟悉度自评（自评作协变量）
   ↓
                 ✗ 不设图素养前测页（见 03_任务定义.md §6.3）
   ↓
INSTRUCTIONS     任务说明（每个任务给一个静态示意）
   ↓
PRACTICE × 5     练习，带反馈与解释（T2 关闭时 4 题）
   ↓
MAIN × 48        正式，无反馈（三个任务各 16 题）
   │  每 12 题 → BREAK（强制 30 秒倒计时）
   ↓
QUESTIONNAIRE    PREVis（4 子量表）+ NASA-TLX
   ↓
DONE             显示完成码（Prolific 用）
```

### 防作弊与质量控制

| 措施 | 实现 |
|---|---|
| 切屏检测 | `document.visibilitychange` → 记录切屏次数 |
| 禁右键/复制 | `contextmenu` / `copy` 事件阻止 |
| 禁后退 | `beforeunload` + 隐藏历史记录 |
| 全屏 | 请求 fullscreen（可选，Prolific 上可能被拒） |
| 过短作答 | 记录 RT，事后过滤 `< 1s` 的 trial |
| Attention check | 正式 trial 里插 2 题（题干含"请选择XX"） |

### 6.2 输出：`data/<pid>.json`

```json
{
  "participant_id": "P001",
```

## 7. 任务实现

> ⚠️ **任务的完整规格（题干、交互、判分公式、记录字段、练习反馈、风险）以 `03_任务定义.md` 为唯一真相源。**
> 本节只给开发方列**实现要点**，避免两处描述漂移。

### 7.1 三个任务与配置开关

| 任务 | 默认 | 配置键 | 完整规格 |
|---|---|---|---|
| **T1** 邻居识别 | 启用 | `CONFIG.tasks.T1.enabled` | `03_任务定义.md` §2 |
| **T4** hub 识别 | 启用 | `CONFIG.tasks.T4.enabled` | `03_任务定义.md` §3 |
| **T2** 邻居计数 | **关闭** | `CONFIG.tasks.T2.enabled` | `03_任务定义.md` §4 |

> **T2 必须完整实现**（交互、判分、记录字段齐全），只是默认不启用。改一个布尔值即可开启。

### 7.2 逐任务的实现要点

**T1（邻居识别）**

| 要点 | 说明 |
|---|---|
| 交互 | **必须同时支持**「单击节点切换选中」与「拖拽矩形框选」，二者等价 |
| 手绘 lasso | 实现为可选（`CONFIG.interactions.freehandLasso`），默认关闭 |
| 提交 | 至少选中 1 个节点才可点 Submit |
| 判分 | 主指标 `Jaccard(选中集, 真实邻居)`，同时记录 precision / recall / exact / 漏选数 / 多选数 |
| 措辞 | 由 `CONFIG.tasks.T1.wording` 决定（`'factual'` 或 `'perceptual'`），交互与判分**完全相同** |

**T4（hub 识别）**

| 要点 | 说明 |
|---|---|
| 交互 | 点击两个高亮节点之一 —— **点击即提交**，不设确认按钮（多一次点击会往反应时注入"找按钮"的噪声） |
| 配对 | `|deg_a − deg_b| ≥ 2` 且 `max/min ≥ 2:1`，且其中一个是 hub |
| 视觉 | 两个目标节点的**填充色、半径、描边样式必须完全一致**——不得暗示哪个度数更高 |
| 判分 | 0/1，是否点中度数更高的那个 |

**T2（邻居计数，默认关闭）**

| 要点 | 说明 |
|---|---|
| 交互 | 数字输入框 + Submit |
| 判分 | 主指标 `|作答 − 真实度数|`（连续值），辅以 exact |
| 风险 | 文献显示这是最难的任务之一（Zoss 2018），有地板效应风险 —— 所以默认关闭 |

### 7.3 三个任务共通的坑

| # | 要点 |
|---|---|
| 1 | **所有非目标节点样式必须完全一致**——不得用大小/颜色/位置暗示度数（见 §2.1） |
| 2 | **目标节点 = 蓝色填充**（`#2196f3`），不放大、不加额外描边 —— 与 §2.3 完全一致 |
| 3 | 计时从**图渲染完成**开始（不是从题目出现开始），用 `performance.now()` |
| 4 | 正式试次**一律不给反馈**；只有练习给 |
| 5 | `layout` 与 `degree_level` **只写进数据文件，绝不显示在界面上** |

## 8. 随机化与平衡

### 8.1 分派逻辑（Latin square）

**这是整个实验最容易做错的一环。** 约束：

```
输入：16 张图（低/高两档各 8 张） × 4 种布局
输出：每个被试【一份】「图 → 布局」的映射，必须同时满足：

  ① 每个被试对每张图只看到【一种】布局   ← 见下方说明
  ② 每种布局恰好覆盖 4 张图              ← 四布局均衡
  ③ 跨被试看，每张图在每种布局下出现的总次数相等
```

> 🔴 **trial 数提醒（最容易写错的地方）**
> T1 / T4 / T2 各跑一次完整的 16 张图，**三个任务共用同一份「图 → 布局」映射**：
> ```
> 每个任务 16 trial  →  三个任务共 48 trial
> ```
> **若误把「每张图只出现一次」读成全局约束，会得出 16 trial——正好是正确值的一半，而且不会报错，只会静默地少收一半数据。**

**算法**（确定性，按 `pid` 派生种子，保证刷新后一致、且可复现）：

```js
function hash(str) { /* 简单字符串哈希 */ }

// 按被试轮转的偏移量（必须均衡分配，见下方警告）
const offset = hash(pid) % LAYOUTS.length;          // 0 | 1 | 2 | 3

// 第 i 张图（i = 0..23）分配到的布局
const layoutIndex = (i + offset) % LAYOUTS.length;

// ★ T1 与 T4 共用【同一个 offset】—— 同一张图在两个任务里是【同一种布局】
//   只有一份映射，不区分任务
```

> **关于「跨任务错位」—— 曾经考虑过，已否决**
> 错位（`offset_T4 = offset_T1 + 1`）能让同一张图在两个任务里显示不同布局，但它**把「自我污染」换成了「交叉污染」**：
> T1 在 KK 布局下学到的结构，会跑到 T4 的 FR 测量里去。
> 同布局重复的偏差方向**可解释**（「读得懂才记得住」→ 偏向本来就好读的布局），交叉污染则**不可归因**。
> 另外，不做错位时设计表述是一句话（「每人每图一种布局」），错位版本要在论文里解释两层轮转。
> 详见 `02_数据方案.md` §7.2 F1。

**为什么满足约束**：

| 约束 | 为什么成立 |
|---|---|
| ① 每图一种布局 | 每张图 `i` 只对应一个 `layoutIndex`，**三个任务共用它** |
| ② 每布局 4 张 | 16 / 4 = 4；且**每档 8 张**，所以每个 (布局, 度数档) 单元恰好 2 张 |
| ③ 跨被试均衡 | `offset` 按被试轮转；四个 offset 各出现 1/4 时，每个 (图, 布局) 组合出现次数相同 |

> ⚠️ **`offset` 必须按被试均衡分配**，不能纯靠哈希（哈希在小样本下会偏斜）。建议：按被试序号取模，或用一个累计计数器。若走 Prolific，可用「已完成人数 mod 4」作为偏移。
>
> ⚠️ **16 张图、4 种布局 = 每人每任务 16 个 trial**，三个任务共 48 个，约 **45–50 分钟**。

### 8.2 试次顺序

- 任务之间**分块**（先做完 T1 再做 T4，或反之，顺序按 pid 交替）
- 块内**随机**（用 pid 派生种子）
- 因为每张图只出现一次，**不需要**额外的「避免连续出现同一图」逻辑

## 9. 刺激生成管线（`tools/build_stimuli.py`）

```
输入：data/eval_out/bench_pipeline_out_0612_ablation_2/graph_details/<graph>_layouts.json
      （每个文件含 15 种算法的布局与坐标）
      图结构：data/dataset/benchmark_test_0312/case1~9.json
      详细规格见 02_数据方案.md §4

步骤：
  1. 读 9 张 case 图（114~1079 节点）
  2. 对每张图，统计每个节点的度数
  3. 对每个度数档（低 2–8 ／ 高 ≥16），选出含该档节点的图，
     每图挑 1 个该档的目标节点，按图名升序取前 8 张
  4. 对每个 (图, 目标节点)，提取四种布局的坐标：
       LPFD ← algorithm == "ablation_exp0_baseline"
       KK   ← "Kamada-Kawai"
       FR   ← "Fruchterman-Reingold"
       FA2  ← "ForceAtlas2"
     ⚠️ 坐标【原样使用】——不裁剪、不重新布局（见 02_数据方案.md §1）
  5. 选目标节点：
       T1: 该档度数节点
       T4: 选一对 (高, 低)，度数比 ≥ 2:1
  6. 匿名化（见 02_数据方案.md §6）
  7. 归一化坐标（见 02_数据方案.md §4.3）
  8. 计算 ground truth（一跳邻域）
  7. 归一化坐标（见 §2.2）
  8. 写出 stimuli.json
```

**产出**：`stimuli/stimuli.json` + 一份 `stimuli/README.md` 说明选图规则与实际选中的图。

## 10. 技术选型

| 层 | 建议 | 理由 |
|---|---|---|
| 渲染 | **原生 SVG** 或 D3.js | SVG 方便做点击命中检测与 lasso 区域判定 |
| 逻辑 | 原生 ES modules | 无需框架，依赖最少，容易交接 |
| 样式 | 手写 CSS | 需求简单 |
| 落盘（模式 A） | `localStorage` + `Blob` 下载 | 无需服务器 |
| 落盘（模式 B） | `fetch` POST 到 Flask / Node | Prolific 需要 |

**为什么不选 React/Vue**：这个应用的复杂度不高，且未来可能需要交给其他人维护。**零构建步骤**（直接 `index.html` + `<script type="module">`）能最大程度降低交接成本。

**本地开发**：`python -m http.server 8000` 即可（因为要 fetch 本地的 stimuli.json，不能直接 `file://` 打开）。
